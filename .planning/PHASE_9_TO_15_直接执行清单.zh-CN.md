## Phase 9：应收、应付、基础结算

### 目标
- 采购订单/入库单能够形成应付记录
- 销售订单/出库单能够形成应收记录
- 可以对一笔应收或应付做最小结算动作
- 页面可以追踪业务单据到财务记录

### 建议 beads
- `Phase 9-应付记录-后端与契约`
- `Phase 9-应收记录-后端与契约`
- `Phase 9-基础结算-后端与契约`
- `Phase 9-财务页面与联动闭环`
- `Phase 9-验证与规划同步`

### 直接执行顺序
1. 先定义最小财务对象：
   - `Payable`
   - `Receivable`
   - `Settlement`
2. 明确来源关系：
   - 采购订单/入库单 -> 应付
   - 销售订单/出库单 -> 应收
3. 先做后端：
   - 模块契约 DTO
   - 领域模型
   - 持久化
   - API
   - 权限
4. 再做前端：
   - 财务页或结算页
   - 应收列表
   - 应付列表
   - 结算动作
   - 业务单据跳转入口
5. 最后验证：
   - 构建通过
   - 能从采购/销售追到财务记录
   - 结算后状态有变化

### 完成判定
- 至少能看到真实应收/应付记录
- 至少能完成一次真实结算
- 采购、销售、库存到财务的链路不断

## Phase 10：工作流、审批中心、通知

### 目标
- 把审批从各页面分散逻辑提升到统一工作流能力
- 提供统一待办中心
- 关键事件可形成通知

### 建议 beads
- `Phase 10-工作流定义与契约`
- `Phase 10-审批实例与待办后端`
- `Phase 10-通知事件与消息后端`
- `Phase 10-审批中心前端闭环`
- `Phase 10-验证与规划同步`

### 直接执行顺序
1. 先定义统一工作流对象：
   - `WorkflowDefinition`
   - `WorkflowInstance`
   - `ApprovalTask`
   - `Notification`
2. 先接最小场景，不要全量替换所有模块：
   - 建议优先接采购申请审核
   - 再接智能体审查
3. 后端先行：
   - 工作流定义注册方式
   - 待办列表 API
   - 审批处理 API
   - 通知落库 API
4. 前端再做：
   - 审批中心页
   - 待办列表
   - 审批历史
   - 通知入口
5. 验证：
   - 提交业务动作后能生成待办
   - 处理待办后业务状态变化

### 完成判定
- 至少一个真实业务流程接入统一审批
- 至少一个通知链路可落库并展示

## Phase 11：报表分析、数据范围权限、单据编号规则

### 目标
- 提供跨模块分析页
- 支持数据范围限制
- 支持单据编号规则配置

### 建议 beads
- `Phase 11-报表契约与统计后端`
- `Phase 11-数据范围权限后端`
- `Phase 11-编号规则后端`
- `Phase 11-分析与治理页面闭环`
- `Phase 11-验证与规划同步`

### 直接执行顺序
1. 报表先做最小横切：
   - 采购
   - 销售
   - 库存
   - 财务
2. 数据权限先做最小范围：
   - 按组织
   - 按仓库
   - 按创建人/归属
3. 编号规则先做配置对象：
   - 模块
   - 前缀
   - 日期段
   - 流水号
4. 前端：
   - 经营分析页
   - 数据范围配置页
   - 编号规则配置页
5. 验证：
   - 不同权限账号看到的数据有差异
   - 新单据编号按规则生成

### 完成判定
- 至少一个分析页可用
- 至少一种数据范围控制生效
- 至少一种编号规则能真正影响新单据

## Phase 12：多组织、多币种、本地化基础

### 目标
- 支持多组织运行
- 核心单据带币种
- 为税票字段留出基础结构

### 建议 beads
- `Phase 12-多组织边界与数据挂接`
- `Phase 12-多币种字段与结算挂接`
- `Phase 12-税票与本地化字段扩展`
- `Phase 12-前端组织与币种闭环`
- `Phase 12-验证与规划同步`

### 直接执行顺序
1. 先给核心对象补组织归属：
   - 客户
   - 供应商
   - 仓库
   - 采购/销售/财务单据
2. 再补币种：
   - 金额
   - 币种代码
   - 汇率字段预留
3. 再补本地化字段：
   - 税率
   - 发票类型
   - 发票抬头或纳税识别号基础字段
4. 前端：
   - 组织切换或组织显示
   - 币种展示
   - 本地化字段录入
5. 验证：
   - 不同组织数据不串
   - 财务记录能显示币种

### 完成判定
- 至少两组织模型成立
- 应收应付或结算记录支持币种字段

## 推荐执行节奏

建议严格按顺序执行：
1. Phase 9
2. Phase 10
3. Phase 11
4. Phase 12
5. Phase 13
6. Phase 14
7. Phase 15

不要跳着做。原因很直接：
- 9 是财务闭环
- 10 是审批治理
- 11 是治理强化
- 12 是多组织和本地化基础
- 13-15 才是制造与计划扩展

## 每个阶段固定收口动作

每一阶段做完都必须执行：
1. `bd update` 或 `bd close` 同步 beads
2. 更新 `.planning/STATE.md`
3. 更新 `.planning/REQUIREMENTS.md`
4. 跑构建：
   - `npm run build --workspace @aeroerp/web`
   - `dotnet build AeroERP.slnx`
5. 如需运行验证，再启动：
   - `dotnet run --project src/AeroERP.AppHost --urls http://localhost:5099`
   - `npm run dev --workspace @aeroerp/web -- --host 0.0.0.0 --port 5173`
